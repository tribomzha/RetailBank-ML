# Приоритизация ручной проверки операций

Документ содержит таблицу ответственности, описание выходного контракта, фолбэк, мониторинг и требования на границах доверия. 

**Бизнес-результат:** рекомендуемый порядок разбора уже существующих сигналов финмониторинга. 
**Выход модели:** числовой балл ранжирования. Он не означает вероятность преступления, не закрывает сигнал и не разрешает действие по платежу.
Все модели, данные, журналы и реестр релизов находятся внутри банка.

**Режим и восстановление**

| Параметр        | Решение и последствия                                                                                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Обработка       | Суточный пакет внутри банка. Сначала теневой режим SHADOW, затем ограниченный ADVISORY после допуска                                                                          |
| Задержка        | Полная версия порядка нужна до смены. Предлагаемый резерв публикации - 15 минут; фактическое окно и p99 измеряются на доступном оборудовании                                  |
| Срочные сигналы | Идут по действующим правилам внутреннего контроля (ПВК) сразу, без ожидания расчёта                                                                                           |
| Повторы         | При временном сбое не более двух повторов через 30 и 120 секунд, если остаётся время до публикации; это стартовые настройки для нагрузочной проверки                          |
| Идемпотентность | Дата среза + версия сигналов + release_id. Lease задания, уникальный event_id, staging и outbox; незавершённый run не публикуется                                             |
| Применение      | API рекомендаций повторно проверяет текущие версии ПВК и дел. Система финмониторинга должна атомарно принять весь порядок; до поддержки этого контракта допустима только тень |
| Отказ           | Потребитель самостоятельно использует сохранённый baseline - действующий порядок.                                                                                             |
| Человек         | Разбирает дела в существующей системе финмониторинга. Техническая job_queue не заменяет очередь сотрудников                                                                   |

Готовность данных остаётся «Разрыв с планом закрытия». 
Технологии Python, Java/Spring Boot и PostgreSQL - предложение реализации. 
Значения TTL признаков, окна расчёта и сроки ПВК фиксируются владельцами до пилота; архитектура не подменяет их произвольными числами.

## 1. Ответственность компонентов и участие человека

### Контейнеры

|Элемент|Тип ответственности|Что делает|Чего не решает|Владелец|
|---|---|---|---|---|
|Операционная система и архив|Существующий источник|Отдаёт разрешённую историю, версии, времена события и загрузки|Не создаёт ML-метку «чистая операция»|Владелец расчётных данных|
|Действующая система финмониторинга|Обычный код + очередь человека|Хранит сигналы, сроки и обязательные приоритеты ПВК, задачи, блокировки задач на время разбора и исходы|Не принимает балл за основание клиентского действия|Руководитель финмониторинга|
|A1. Суточный расчёт|Код + один обучаемый метод|Создаёт снимок признаков, баллы и проект допустимого порядка|Не вызывает платёжные API|Команда ML и инженер данных|
|A2. API рекомендаций|Обычный код|Создаёт задание по расписанию, публикует целую версию порядка, принимает обратную связь, переключает режим|Не отменяет ПВК, не меняет завершённые или уже взятые дела|Команда сервиса|
|A3. Снимки|Хранилище|Версии признаков, ссылки на первоисточники, состав выборки и вероятность включения|Не служит самостоятельной копией полного клиентского досье|Владелец данных и платформа|
|A4. Реестр и job_queue|Хранилище + техническая очередь|Задания с lease, попытки, staging, outbox, версия опубликованного порядка, раздельные экспертные исходы|Не заменяет очередь сотрудников|Команда сервиса|
|Внутренний реестр релизов|Внутренний контур релизов|Хранит одобренный комплект кода, модели, шкалы и политик для развёртывания в банке|Не разрешает автоматическое обучение на обратной связи|MLOps и ИБ|
|Сотрудник финмониторинга|Человек в существующем процессе|Изучает факты, фиксирует основание/его отсутствие/недостаток сведений, выполняет действие по процедуре|Не обязан верить рангу и может обоснованно его переопределить|Руководитель смены|

Отдельный брокер сообщений и сетевой сервис модели для этого пилота не нужны. Один суточный job читает снимок; job_queue/outbox в PostgreSQL достаточно для управления заданиями и публикацией. Это не означает загрузку всех 25 млн операций в очередь заданий: большая история поступает пакетным экспортом в расчёт признаков. При необходимости потокового режима вопрос брокера и сервисного инференса открывается заново.

### Компоненты A1

| Компонент                 | Код / модель                         | Вход → выход                                                        | Основная проверка                                                                                                             |
| ------------------------- | ------------------------------------ | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| A1.1 Управление прогоном  | Код                                  | Job с cutoff и версиями → один воспроизводимый run                  | Уникальный ключ задания, lease, полный набор входных версий, отсутствие публикации неполного run                              |
| A1.2 Подготовка признаков | Код                                  | Разрешённая история → числовые/категориальные признаки и provenance | `event_time ≤ as_of`, данные были доступны на срезе; полнота, дубли, сторно, минимальная история, поддержанный сегмент        |
| A1.3 Ранжировщик          | Обучаемая статистика                 | Вектор → raw_score                                                  | Один выбранный кандидат: профиль эмпирических процентилей либо Isolation Forest                                               |
| A1.4 Проверка и шкала     | Код + замороженная референсная шкала | raw_score → priority_score или отказ                                | Конечность, ожидаемое направление, совместимые версии; приведение к шкале 0–1 на фиксированном референсе                      |
| A1.5 Политика очереди     | Код                                  | Баллы + ПВК + бюджет часов + baseline → проект порядка              | Неприкосновенность обязательных дел, сроки, одинаковое объединение эпизодов, зона воздержания и отсутствие вытеснения отказов |
| A1.6 Контракт и staging   | Код                                  | Проект → валидный результат и outbox                                | Идентификаторы, источник, версии, уникальность, полнота набора; запись одной транзакцией                                      |

Профиль процентилей обучается только в смысле оценки распределения на референсной истории; агрегирование отклонений задаётся кодом. Isolation Forest изучает сочетания признаков без готовой разметки схем. Оба метода сравниваются по одному протоколу из паспорта. При сопоставимом эффекте остаётся более простой профиль. Выбор победителя пока не сделан.

Manifest релиза хранит ID обучающего/референсного снимка, период построения, feature_spec, seed, версии зависимостей, веса или профиль, способ шкалирования, результаты приёмки и согласовавших релиз. Снимок обучения отделён по времени и эпизодам от закрытой проверки. В runtime используются только артефакты замороженного релиза, статистика не переобучается молча на очередном суточном пакете.

Шкала A1.4 нужна для единообразного направления и контроля стабильности. Если кандидат уже выдаёт согласованный процентиль, повторное преобразование не выполняется. Это **не калибровка вероятности преступления**: для неё нет надёжного эталона. Порог блокировки платежа отсутствует.

В первом варианте используются сумма, время, канал, ОКВЭД, контрагент и разрешённые агрегаты истории: частоты, обороты, концентрация контрагентов и временные интервалы. Точные окна и минимальная длина истории фиксируются до теста в feature_spec. Назначение платежа и свободный текст исключены. Retrieval, промпт, LLM, агентные инструменты и дообучение языковой модели в №1 не нужны. Факты для карточки рассчитываются кодом, а не генерируются как объяснение модели.

### Место человека и политика порядка

1. Система финмониторинга немедленно обрабатывает новые обязательные сигналы по действующим ПВК. Она не ждёт суточного ML-пакета. Существующие внешние сигналы, включая ЗСК, приходят своим действующим маршрутом; сервис ранжирования не создаёт новую интеграцию с ЗСК.
    
2. Для каждого прогона фиксируются все открытые сигналы, baseline, сроки, сведения о взятых в работу задачах и версии ПВК. Это может быть накопленная очередь, а не только сигналы за один день.
    
3. Вероятностный контроль формируется из полного входящего потока до ранжирования. Сохраняются страта, N, n, π и seed отбора. План паспорта - 500 контрольных операций за четыре недели: 350 без сигнала и 150 с сигналом. Это канал оценки, а не расширение модельной детекции на весь поток.
    
4. Из часов смены вычитаются обязательные проверки, контроль, вторые чтения и арбитраж. Остаток H даёт `K = floor(60 × H / t)`, где t - измеренное число минут на дело. K ограничивается числом доступных дел. При H ≤ 0 модель не получает рабочих мест.
    
5. Связанные операции группируются по одной версионной процедуре в обеих очередях. Если готовых связей нет, допускается только согласованное детерминированное правило. Предлагаемое агрегирование - максимум допустимых баллов операций эпизода; при отказе по существенной операции эпизод сохраняет baseline. Параметры группировки и агрегирования замораживаются до эксперимента.
    
6. Из baseline фиксируются места обязательных, уже взятых, просроченных, неподдержанных и отказных дел. Модель переставляет только остальные допустимые дела в оставшихся местах, с ограничением максимального ожидания из ПВК/политики смены. Нельзя присвоить отказному делу нулевой балл и отправить его в конец. Низкий балл не закрывает сигнал.
    
7. Вблизи границы K применяется зона воздержания: если разница нормализованных баллов меньше настроенного ε либо небольшое согласованное возмущение признаков меняет попадание в K, порядок соответствующей группы сохраняется по baseline. ε устанавливается на настроечном периоде по стабильности и стоимости дополнительных разборов; универсального значения 0,5 нет. Для точных равенств применяется воспроизводимая сортировка по возрасту и ID.
    
8. A2 перед публикацией снова читает актуальные ПВК, сроки и состояния дел. Изменение версии делает прежний проект непубликуемым. Новые сигналы до следующего расчёта идут по baseline. Взятая сотрудником карточка не «прыгает» при смене ранга.
    
9. Сотрудник получает обычную задачу финмониторинга с фактами и источниками. В слепой приёмке балл и канал отбора скрываются сервером, а не только интерфейсом. В рабочем режиме сотрудник видит роль рекомендации, может сменить приоритет с причиной. Эскалация, исход расследования и формальное подтверждение сохраняются отдельными событиями.
    

Модель не устраняет разницу между 35 тыс. сигналов и 10 тыс. разборов. Если обязательный объём превышает фонд времени, руководителю смены нужен план ресурсов и обработки задолженности; перестановка очереди не объявляется решением нехватки людей. Контрольные 120 часов за четыре недели при исходных 12 минутах и 20% вторых чтений также требуют реального выделения времени.

### Цена обеих ошибок и уровень автоматизации

| Ошибка                                       | Цена в данной постановке                                                                                                                               | Как это ограничивает автоматизацию                                                                                                   |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| Правомерный эпизод получил высокий приоритет | Около 12 минут первичного разбора по исходному процессу и вытеснение другого дела; при необоснованном последующем действии - задержка платежа и жалоба | K связан с фактическими часами; измеряется отдача на 100 ч. Высокий ранг не даёт права блокировать платёж, сотрудник проверяет факты |
| Обоснованный эпизод получил низкий приоритет | Поздний разбор, возможный пропуск схемы и надзорные последствия; денежная цена в кейсе не определена                                                   | Сохраняются ПВК, возрастные ограничения и независимый контроль. Низкий ранг не означает «чисто» и не снимает обязательную проверку   |
| Модель воздержалась при недостатке сведений  | Сохраняется стоимость штатного разбора, выигрыш автоматизации не получен                                                                               | Выбирается baseline вместо ложной определённости; доля отказов и затраченные часы входят в оценку эффекта                            |

Поэтому рабочая точка - доступная глубина очереди, а не универсальный порог риска. Цена ложного приоритета ограничивает K и требования к полезности; цена позднего разбора ограничивает допустимую перестановку и не позволяет автоматически отбрасывать низкие баллы. Перевод модели в принятие решений по платежу потребовал бы новой постановки, другого эталона и отдельного решения о допустимости.

## 2. Выходной контракт

Контракт описывает **рекомендацию по очереди**. Ниже приведены его обязательные поля и правила обработки. Дополнительные `ranking-response.schema.json`, `ranking-scored.example.json` и `ranking-abstain.example.json` в архитектурном архиве содержат машинную схему и два синтетических примера именно этого контракта. Пакет публикации дополнительно содержит полный список ID, число результатов, контрольную сумму и версию порядка.

| Поле                                               | Обязательность и смысл                                                                         | Проверка перед публикацией                                                                      |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| schema_version, recommendation_id, run_id, mode    | Всегда; режим `SHADOW` или `ADVISORY`                                                          | Поддержанная схема, уникальность рекомендации в run                                             |
| operation_id, episode_id, case_id, case_version    | Всегда; ссылки на существующие объекты                                                         | Принадлежность доступному делу, совпадение версий; связь с эпизодом                             |
| as_of, generated_at, expires_at, input_snapshot_id | Всегда                                                                                         | Причинный порядок времени; снимок воспроизводим; рекомендация не просрочена                     |
| release                                            | Всегда: method, model_version, feature_version, reference_version, policy_version, code_digest | Все части входят в один одобренный manifest                                                     |
| status                                             | `SCORED`, `ABSTAIN` или `FAILED`                                                               | Отказ/сбой сохраняется явно                                                                     |
| raw_score, priority_score                          | Числа при `SCORED`; иначе null                                                                 | Конечные значения, priority_score от 0 до 1. Ноль не заменяет отсутствие                        |
| score_meaning                                      | Всегда `RANK_ONLY`                                                                             | Нельзя преобразовать в вероятность схемы или решение по платежу                                 |
| queue                                              | lane, action, rank, baseline_position, deadline_at, queue_version                              | RANK_ELIGIBLE допустим только для DISCRETIONARY и SCORED; для остальных rank=null               |
| reasons                                            | Массив кодов; непустой при отказе                                                              | Только согласованный справочник: NO_HISTORY, STALE_FEATURES, UNSUPPORTED_SEGMENT и др.          |
| evidence                                           | Проверяемые признаки, окно и ссылки; непустой для SCORED                                       | Значения сверены со снимком; ссылка действительно подтверждает факт                             |
| source_refs                                        | Хотя бы одна ссылка даже при отказе — на исходный сигнал/операцию                              | Тип, ID, версия, время и внутренний URI из серверного resolver; доступ проверяется при открытии |
| validation                                         | `PASSED` и перечень выполненных проверок                                                       | Это проверка оболочки ответа; проблемы качества представлены status/reasons                     |
| authority                                          | `RECOMMENDATION_ONLY`                                                                          | Получатель не трактует ответ как разрешение клиентского действия                                |

`bank://operations/...` и `bank://signals/...` в примерах - схема внутренних ссылок проекта, а не существующие внешние URL. Интерфейс разрешает такую ссылку в маршрут банковской системы и повторно проверяет права. Произвольный URL из данных модели не открывается сервером.

Проверки идут в два этапа. A1.6 проверяет JSON Schema, все finite-числа, наличие и версию источников, полноту набора и совместимость релиза. A2 заново проверяет актуальные сроки ПВК, возраст результата, очередь, состояние дела и права до смены порядка. Даже корректный JSON недостаточен для принятия рекомендации. Перед клиентским действием действующая система выполняет свои бизнес-проверки и требует уполномоченное решение сотрудника; AI-сервис не обладает соответствующим методом или сервисным доступом.

При полном отсутствии источника запрос получает техническую ошибку задания и не публикует вымышленную рекомендацию. Если источник сигнала есть, но история неполна, публикуется валидный `ABSTAIN` со ссылкой на сигнал, null-баллами и `KEEP_BASELINE_ORDER`. Если не завершён весь run, частичный результат остаётся диагностикой и не становится рабочим порядком.

### Типы и вложенные структуры

Все поля верхнего уровня из таблицы обязательны. Идентификаторы и версии - непустые строки; даты - строки date-time с часовым смещением. Неизвестные поля отклоняются. `mode` принимает SHADOW или ADVISORY. В режиме SHADOW результат хранится для сравнения и не изменяет рабочую очередь.

|Структура|Обязательные поля и ограничения|
|---|---|
|release|`method`: PEER_PERCENTILE или ISOLATION_FOREST; строки `model_version`, `feature_version`, `reference_version`, `policy_version`, `code_digest`. Метод в примере не означает выбор победителя|
|queue|`lane`: MANDATORY, DISCRETIONARY или CONTROL; `action`: KEEP_MANDATORY_ORDER, RANK_ELIGIBLE, KEEP_BASELINE_ORDER или CONTROL_SAMPLE; `baseline_position`: целое ≥ 1; `queue_version`: строка; `deadline_at`: дата либо null, если срока нет; `rank`: целое ≥ 1 только при RANK_ELIGIBLE, иначе null|
|evidence[]|`feature`, числовое конечное `value`, `unit`, даты `window_start`/`window_end`, непустой массив `source_ref_ids`. Все ссылки разрешаются в source_refs того же ответа|
|source_refs[]|`source_id`, `kind` из OPERATION/SIGNAL/FEATURE_SNAPSHOT, `record_id`, `version`, `as_of`, `uri`. Ссылка формируется приложением и указывает на доступную версию источника внутри банка|
|reasons[]|Согласованный набор: MISSING_FEATURES, STALE_FEATURES, NO_HISTORY, UNSUPPORTED_SEGMENT, OUT_OF_SUPPORT, ABSTAIN_NEAR_CUTOFF, RULE_OVERRIDE, MODEL_INVALID, INVALID_EVIDENCE, SOURCE_UNAVAILABLE, RUNTIME_LIMIT, STALE_CASE_VERSION|
|validation|`status=PASSED`, непустой список `checks`. PASSED подтверждает допустимость оболочки ответа; не превращает ABSTAIN или FAILED в успешный скоринг|

### Три варианта результата

|Состояние|Балл и доказательства|Что делает получатель|
|---|---|---|
|SCORED|Конечные raw_score и priority_score; priority_score в [0, 1]; evidence и source_refs непустые|Может изменить только разрешённые места DISCRETIONARY после повторной валидации; обязательные и контрольные маршруты сохраняются|
|ABSTAIN|Оба балла и rank равны null; есть причина и ссылка на исходный сигнал/операцию|Сохраняет baseline либо обязательный/контрольный маршрут соответствующего дела; не ставит отказ в конец|
|FAILED|Оба балла и rank равны null; причина технического сбоя; допустимая ссылка на исходный объект сохранена|Использует штатный порядок; системный сбой не позволяет публиковать частичный run. Если нет даже проверяемого исходного объекта, выдаётся ошибка задания без рекомендации|

Ошибка валидации не маскируется объектом с `validation.status=PASSED`. Такой результат остаётся диагностикой до исправления либо преобразуется кодом в корректный отказ с действительным источником. Любое клиентское действие выполняется отдельно существующей процессной системой после решения уполномоченного сотрудника.

**Откат:** система финмониторинга переводит `ordering_mode` в BASELINE и отменяет ещё не применённые рекомендации. Уже взятые в работу дела и выполненные решения сотрудника не меняются. Повторный расчёт использует исправленный снимок и согласованные версии. Возврат на предыдущую модель допустим только вместе с совместимыми признаками, шкалой и политикой.

Зависшее задание теряет lease и восстанавливается с подтверждённого состояния. После лимита попыток оно переводится в DEAD для сопровождения; следующие задания не блокируются. Увеличение числа повторов не является способом скрыть неисправность источника или нехватку мощности.

## 4. План мониторинга

| Слой                 | Что измеряем                                                                                                                      | Что запускает действие                                                                                                             | Действие / ответственный                                                                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Вход                 | Полнота по дням относительно источника; watermark; дубли/сторно; пропуски; версии правил; история и доля неподдержанных сегментов | Отсутствует обязательное поле, неполный снимок, сломана версия                                                                     | Отказ кейса или run, baseline; инженер данных                                                                                    |
| Распределения        | Признаки и баллы по сегментам; доля отказов; новые категории; доли типологий в верхушке                                           | Выход за контрольный диапазон сопоставимых недель на двух прогонах; пороги диапазона фиксируются до пилота                         | Анализ дрейфа и новая разметка; при нарушении области применения — локальный fallback. Дрейф сам по себе не доказывает ухудшение |
| Исполнение модели    | Время/память, invalid-score, совпадение release manifest, стабильность топ-K                                                      | NaN/несовместимый релиз/ошибка источника; p99 не помещается в окно                                                                 | Не публиковать, откат к baseline; MLOps и сопровождение                                                                          |
| Техническая очередь  | Возраст job, lease, попытки, DEAD, lag outbox, завершённость run                                                                  | Нет полного результата к сроку публикации; результат не подтверждён получателем                                                    | Baseline; оповещение дежурного; без частичного переключения                                                                      |
| Очередь людей        | p50/p95 ожидания, возраст старейшего дела, обязательные дедлайны, объём/скорость, часы H, разборы и доля «недостаточно сведений»  | Любое нарушение обязательного срока/маршрута по вине порядка; прогноз нехватки часов                                               | Немедленный baseline и руководитель смены; отдельный план устранения задолженности                                               |
| Разметка             | Покрытие страт, известная π, доля второго чтения, κ и положительное согласие                                                      | Потеря π, пустая страта, κ < 0,70 или положительное согласие < 0,80; мало положительных пар                                        | Остановить выводы по полному потоку/допуск; исправить протокол и собрать дополнительную двойную разметку                         |
| Модельная полезность | Обоснованные эпизоды на 100 ч, доля обоснованных в верхушке, неопределённость, результаты по типологиям                           | Не выполнено хотя бы одно условие приёмки: прирост ≥ 1 эпизод/100 ч; нижняя 95%-я граница прироста > 0; сохранены важные типологии | Не включать в работу; пересмотреть признаки/метод и провести новую независимую приёмку                                           |
| Клиентский эффект    | p95 ожидания, снятые приостановки и жалобы на 1000 сопоставимых операций                                                          | В рабочем сравнении ухудшение относительно одновременного контроля выше заранее принятого допуска                                  | Вернуть baseline и расследовать причину; владелец финмониторинга. В тени причинный эффект не заявляется                          |

Метрики полезности считаются по фактическим минутам, с одинаковым объединением эпизодов и учётом неопределённых в затратах. Контрольные операции вне сигналов анализируются отдельно с 1/π; исторические 4% эскалаций не подставляются как истинная precision. Поздние исходы мониторятся отдельными созревающими когортами, без превращения незавершённых расследований в отрицательные метки.

До согласования иной величины допуск клиентского ухудшения - «без ухудшения» согласно паспорту. Правило статистического сравнения и размер окна фиксируются до рабочего пилота; отдельный шумный процент без достаточной выборки — повод разбирать сигнал, а не утверждать доказанный вред. Потеря обязательного дела или действие по платежу без требуемого участия человека - немедленный stop независимо от статистики.

**Периодичность:** вход, manifest, контракт и полнота проверяются на каждом run; состояние очереди и сроки - непрерывно по событиям процессной системы; полезность и клиентский эффект - на заранее зафиксированных сопоставимых окнах, с учётом дозревания исходов. Контрольные диапазоны дрейфа определяются на настроечном периоде и замораживаются до независимой проверки.

**Повторная проверка:** новые сегменты, существенное изменение источника, ПВК, признаков, зависимостей или модели создают новый цикл приёмки. Исправления сначала проходят регрессионные сценарии и тень. Обратная связь сама не переобучает модель и не меняет пороги.

**Условие промышленного запуска:** достижение качества само по себе недостаточно. По актуальному ADR-001 дополнительно нужны клиентские ограничения и подтверждённая экономика либо отдельно одобренный измеримый риск-бюджет. Текущая архитектура разрешает проектирование и подготовку пилота, но не объявляет промышленный допуск полученным.

## 5. Угрозы на границах доверия

Номера соответствуют оранжевому пунктиру на C4. 

|Граница на C4|Угроза|Что делаем и как проверяем|
|---|---|---|
|**Расчётные данные → A1/A3**; №1 C2/C3|Избыточный доступ к банковским данным, подмена среза, утечка через выгрузки и журналы|Read-only роль на разрешённый набор; псевдонимы участников; исключить свободный текст; фиксировать обе даты, происхождение и хеш снимка. Шифрование каналов/хранилищ, сроки хранения и очистки по допуску владельца. Проверка: запрещённые поля не проходят экспорт, будущая запись не попадает в признаки, логи не содержат платежей|
|**A1.3 → A1.4**; №1 Component|Недоверенный/ошибочный балл принимается как команда; NaN, несовместимая модель, поддельное объяснение|Вызов в памяти тоже пересекает логическую границу. Строгий адаптер результата, finite, версия, домен; факты строятся кодом. У модели нет интерфейса платежа. Проверка: NaN, лишнее поле и «BLOCK» отклоняются; обычный выброс остаётся аномалией только в поддержанном домене|
|**A2 ↔ система финмониторинга**; №1 Container|Сервисный аккаунт меняет ПВК/платёж, подмена человеческого исхода, replay, просроченный ранг; утечка оператору|Отдельная роль только на чтение сигналов и запись рекомендации, без платёжных прав. Аутентификация сервисов, idempotency/event ID, версии и TTL, RBAC рабочего места, неизменяемый аудит actor_id. Решения подписываются контекстом пользователя процессной системы. Проверка: повтор не меняет эффект; старое/чужое дело недоступно; обязательный маршрут не переопределяется|
|**Внутренний реестр релизов → исполняющие контейнеры банка**; все Container|Подмена или неразрешённая версия весов/зависимостей, исполнение вредоносного кода, внешняя телеметрия|До допуска в реестр проверяются происхождение артефакта, лицензия, SBOM, зависимости и изолированная сборка. На границе развёртывания сверяются manifest, разрешённая версия и digest/signature; runtime получает read-only комплект. Не исполнять pickle/joblib и remote code из неутверждённого источника; для собственных сериализованных моделей — только подписанный внутренний build. Исходящий доступ запрещён по умолчанию. Проверка: неподписанный/изменённый релиз и сетевой callback блокируются|

Журналы и мониторинг остаются внутри банка: идентификаторы трассировок, версии, статусы и агрегаты без содержимого платежей. Экспорты, резервные копии и временные файлы подчиняются тому же режиму доступа и удаления. Вывод информации во внешние сервисы мониторинга этим проектом не предусмотрен; новый внешний поток потребует отдельной границы на C4 и пересмотра ADR.
